Preprocessing 시스템 구조 / 연산 위치 / 서버 배포 방향

이번 버전은 어디서 연산이 일어나는지를 분명히 구분했습니다. 현재 구조에서는 브라우저 UI, 프론트엔드 로직, Python backend, 산출물 저장이 모두 로컬 PC(또는 VDI 세션 내부) 자원을 사용합니다. OPC UA 조회도 서버가 아니라 로컬 환경에서만 가능합니다. 서버 배포는 가능하지만 OPC UA는 방화벽 때문에 직접 연동되지 않습니다.

1. 현재 실제 실행 구조

현재는 서버형 SaaS 구조가 아니라 로컬 실행형입니다. 연산 위치를 기준으로 보면, 사용자 화면과 전처리 계산, 파일 저장이 모두 로컬 자원에서 처리됩니다.

2. 현재 기능별 연산 위치

팀원들이 가장 헷갈려하는 부분을 기능 단위로 쪼개면 아래처럼 정리할 수 있습니다.

3. OPC helper 조회가 서버가 아니라 로컬인 이유

현재 helper 태그는 단순 REST API가 아니라, 로컬 Python backend가 OPC UA 서버에 직접 붙어서 history/current를 읽는 구조입니다.

sequenceDiagram participant U as 사용자 participant B as 브라우저/Frontend participant L as Local Python backend participant O as OPC UA 서버 U->>B: helper 태그 선택 B->>L: POST /api/opc/helper-values Note over B,L: 로컬에서만 호출 가능 L->>O: OPC UA history/current read O-->>L: raw values 반환 L-->>B: helper values 응답 B-->>U: 필터/소팅용 helper 컬럼 표시
서버형 backend가 OPC UA에 바로 붙지 못하는 이유는 방화벽입니다. 즉, OPC UA 함수 자체가 로컬에서만 연동됩니다.

4. 서버 배포 시 가능한 구조

서버 배포를 하면 프론트/백엔드/세션/파일관리는 서버로 옮길 수 있지만, OPC UA 직접 연결은 서버에서 막힙니다. 따라서 서버형은 두 가지로 나뉩니다.

flowchart LR user[사용자 브라우저] subgraph SERVER[사내 포털 서버] portalFE[Portal Frontend] portalBE[Portal Backend
세션 · 업로드 · 실행 · 다운로드] sess[세션 저장소] preset[프리셋/즐겨찾기 저장소] end subgraph LOCALONLY[로컬/VDI 전용 구간] sidecar[Local OPC sidecar 또는 local backend] opc[OPC UA 서버] end user --> portalFE --> portalBE portalBE --> sess portalBE --> preset sidecar --> opc portalFE -. 필요 시 로컬 bridge .-> sidecar
  • 서버에서 가능한 것: 파일 업로드, 세션 관리, 전처리 실행, 산출물 다운로드, 프리셋/즐겨찾기 관리
  • 서버에서 막히는 것: OPC UA 직접 조회
  • 해결 방향: OPC helper 기능은 로컬 sidecar / local backend와 연결하는 하이브리드 구조

5. 추천 운영 모델

팀 관점에서는 아래 3개를 분리해서 이해하는 것이 좋습니다.

flowchart TD A[Mode 1 - 현재]\n로컬 단독 실행 --> A1[UI/전처리/저장/OPC 모두 로컬] B[Mode 2 - 서버형]\n포털 배포 --> B1[UI/세션/산출물은 서버\nOPC helper는 미지원 또는 별도 연동] C[Mode 3 - 하이브리드]\n추천 확장안 --> C1[포털 서버 + 로컬 OPC sidecar\n같은 UI, 다른 backend 경로]
가장 현실적인 방향은 same frontend, different backend 입니다. 다만 OPC helper는 서버가 아니라 로컬 sidecar를 통하는 하이브리드가 되어야 합니다.

6. 권장 API 분리 방향

서버형과 로컬형을 같이 가져가려면 API도 역할을 분리해서 보는 게 좋습니다.

flowchart TD A[로컬 전용 API] --> A1[GET /api/tags] A --> A2[GET /api/opc/current] A --> A3[POST /api/opc/helper-values] B[서버 공통 API] --> B1[POST /api/session/upload] B --> B2[POST /api/preprocess/run] B --> B3[GET /api/session/preview] B --> B4[GET /api/session/download] B --> B5[GET or POST /api/presets] B --> B6[GET or POST /api/favorites]
  • 로컬 전용: OPC가 엮인 API
  • 서버 공통: 업로드/전처리/다운로드/프리셋
  • 핵심 구분: OPC API는 서버로 못 올리고, 나머지 업무 API는 서버형으로 올릴 수 있음
최종 정리: 현재 구조는 “브라우저만 로컬”이 아니라 브라우저, 프론트엔드 로직, Python backend, 산출물 저장, OPC 연동까지 모두 로컬 자원 사용입니다. 서버 배포는 가능하지만, OPC UA는 방화벽 때문에 서버에서 직접 연결되지 않으므로 helper 기능은 로컬 sidecar 또는 local backend와 분리 설계해야 합니다.
